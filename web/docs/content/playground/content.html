How it works

The page declares its pattern up top:

{% alias "/playground/:section" %}

The build extracts the alias and registers it in the manifest's route trie. At request time the trie matches the URL, binds the captured value to the name section, and the dispatcher hands those bindings to the hole renderer. The renderer exposes them inside any hole body via the _params key: 

{% hole "" %}
<code>{{ ._params.section }}</code>
{% endhole %}

The hole here uses an empty SQL string. That's a no-DB hole — the template runs exactly once with just the URL bindings, no rows. Combine an empty hole with a SQL hole and you get a route whose output is part SQL data, part URL parameter: 

{% hole "SELECT name, email FROM users WHERE id = ?" %}
<h1>{{ .name }}</h1>
<p>ID requested: {{ ._params.id }}</p>
{% endhole %}

What this means for APIs

Bindings reach the response renderer the same way for every path — whether it ends in a JSON-shaped content.html or an HTML one, whether it queries SQL or just echoes the URL. The engine's content pipeline is enough on its own to express REST-shaped endpoints; you don't need a separate "action handler" path for typical JSON-returning routes.

Go handlers (the actions.RouteCtx path) still exist for genuinely-non-HTML responses, server-orchestrated work, or endpoints that need direct access to Req / Resp. But the boundary is "do you need to run Go code per request?" — not "is it dynamic?"

Caching with bindings

The output cache keys by (route, bindings hash), so /playground/about and /playground/users become two separate entries — each renders once, then serves from cache forever (until its underlying tables write).

For high-cardinality URLs (per-session UUIDs, unique IDs only hit once), the LRU evicts cold entries naturally; those URLs effectively render fresh every time. For repeated dynamic URLs (popular products, common usernames), throughput matches static pages.
