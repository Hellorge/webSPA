What's inside

Four ideas, doing all the heavy lifting.

Gogogo isn't a framework. It's a small set of decisions that move work from request time to build time — and then commits to the consequences.

Trie routing

Per-segment trie with :id params and *path catch-all. Lookup is O(depth) — bounded by URL structure, not route count. Static and dynamic sit in one universal flow.

Holes

Mark live-data spots in HTML. Build pre-extracts the body. Runtime splices SQL rows in. The envelope never re-renders.

ActionFile

Files past a size threshold skip the manifest and serve via sendfile(2). Range requests built in. Bytes go kernel→kernel.

Multi-site

One binary, many manifests. Each [[site]] in config.toml bakes its own manifest, dispatched by Host header.

The shape of a page.

Drop a single content.html. The build walks your tree, renders your templates, compresses three encodings, and bakes a manifest the runtime mmap's into place. No metadata sidecar — alias, head tags, queries live inline as Jinja-style tags.

You write content. The engine handles the wire.
