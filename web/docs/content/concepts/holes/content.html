Holes

A hole is a marked spot in your HTML where the engine splices fresh SQL data at request time. The envelope around it — layout, text, classes — is baked once at build. Only the rows change.

The shape

One inline tag declares the SQL and wraps the per-row body template: 

{% hole "SELECT title, summary, date FROM news ORDER BY date DESC" %}
<li>
  <strong>{{ .title }}</strong> — {{ .summary }}
</li>
{% endhole %}

Inside the body, the dot context is the current SQL row as a map. {{ .title }} reads the title column. The body repeats once per row. The engine uses Go's stdlib text/template for the body — you have {{ "{{ if }}" }}, {{ "{{ range }}" }}, {{ "{{ with }}" }}, printf, html, every builtin.

What happens at build

  1. The build byte-scans each page's content.html, extracts every hole's SQL and body, and stores them in parallel arrays indexed by appearance order. The hole site in the HTML is replaced with a unique marker carrying the hole's index.
  2. text/template renders the page envelope normally — {{ "{{ extends }}" }}, {{ "{{ block }}" }}, {{ "{{ template }}" }}, all of it. The markers pass through untouched.
  3. The build scans the rendered output for the markers, records each byte offset, strips them. The result is a clean envelope plus a list of (position, sql, body) tuples baked into the manifest.

What happens at request time

  1. The router finds the route. The envelope is mmap'd bytes from the manifest.
  2. For each hole:
    • Run the SQL through fastdb's row cache — hit returns cached rows, miss runs SQLite and caches.
    • Run the per-row body template once per row, appending output to a buffer.
  3. Splice the hole output into the envelope at the recorded offset, then write to the connection.

The hole's template context

Three things show up under dot in a hole body:

  • SQL row columns as .columnname. Maps directly to the result set.
  • URL bindings as ._params.name when the route is registered with a param/catch-all pattern. See routing.
  • Nothing else — no global state, no Request reference. By design.

Empty-SQL holes

A hole with empty SQL runs its template exactly once with just the URL bindings — no DB call at all. Useful for pure URL-derived content: 

{% hole "" %}
<h1>User {{ ._params.id }}</h1>
{% endhole %}

Caching layers

Hole pages without URL params benefit from three independent caches:

LayerSkips on hit
Output cache Everything — SQL, template, splice, compression
fastdb row cache SQLite parse + execute + row materialisation
Template parse cache Re-parsing the body template (parsed once at server load)

All three share one invalidation signal: fastdb's write events. A write to a referenced table drops the matching output-cache entries, drops the row-cache entries, and the next request renders from scratch. Pages with URL bindings cache by (route, bindings) — each distinct URL is its own entry, same lifecycle.

Why it's fast

  • Layout never re-renders. The envelope is pre-baked bytes; the runtime just writes them.
  • Positions are precomputed. No re-parse, no AST walk, no string search at request time.
  • SQL only runs when needed. Cached pages skip the DB entirely. Pages without holes never touch SQLite.
  • Bindings are first-class. ._params is just a key in the template context; no special interpreter pass.

Live: scalar query

A hole works for a single-row scalar too — the body runs once.

News rows in DB: {% hole "SELECT COUNT(*) AS n FROM news" %}{{ .n }}{% endhole %}

What you can't do

  • Holes can't nest. The body is a per-row template, not a full template program.
  • Holes can't share state across sites — each site's manifest carries its own.
  • Hole bodies can't run arbitrary Go code (use an action handler for that). They run text/template with stdlib funcs — full grammar, no escape hatches.
  • A hole's SQL is fixed at build time. Per-request SQL with bound parameters from the URL is a planned extension, not present today.
