fastdb

Gogogo's read-side SQLite layer. Talks to modernc.org/sqlite/lib directly — no database/sql wrapper, no per-request prepare, no row-shape reflection. Plus a query-result cache that knows which tables each cached query reads from, and invalidates by table-write signal — not by TTL.

What's in it

  • Connection pool. Fixed-size, one libc TLS per conn. SQLite WAL mode lets many readers run in parallel; the pool just hands one out per query.
  • Prepared-statement cache per connection. A SQL string is compiled once, then reused. Repeat queries skip SQLite's parser entirely.
  • Query-result cache. Materialised rows keyed by SQL text, with the tables each query references recorded for invalidation.
  • Update-hook invalidation. SQLite calls back on every INSERT/UPDATE/DELETE; we drop only the cache entries referencing the written table.
  • data_version safety net. A 1Hz watcher catches writes that bypass our pool entirely (CLI sessions, other processes).
  • Per-table bypass. Tables with sustained high write rates flip out of caching automatically so they don't thrash everyone else's entries.
  • Subscribe API. Anything else (e.g. the renderer's output cache) can listen for write events and invalidate its own state in lockstep.

The cache, end to end

Lookup

rows, err := fastdb.QueryEach("SELECT title FROM news ORDER BY date DESC LIMIT 4", visit)

The pool does this:

  1. Hash the SQL string → cache key.
  2. Look up the table set we extracted last time (or extract once if first occurrence): scan for FROM / JOIN + identifier. Subqueries, CTEs, quoted-identifier tables → nil = "uncacheable, run fresh."
  3. Check each referenced table's bypass state. If any is in a cool-down (recently wrote heavily) → skip cache, run fresh.
  4. Map probe by key. Hit → iterate cached rows, call visit. Miss → run SQLite, snapshot each row, cache, then call visit.

Invalidation

SQLite's sqlite3_update_hook fires on every row write, with (op, table, rowid). fastdb's callback:

  1. Bump the table's per-second write counter. If past bypass_threshold → flip to bypass for the cool-down window.
  2. Look up the reverse index: map[table]→set[cacheKey]. Drop those keys. Other tables' entries are untouched.
  3. Fan out to any subscribers (next section).

The data_version watcher

SQLite's PRAGMA data_version returns a number that increments when ANY OTHER connection writes to the database. Our watcher polls it once per second on one pool connection. On a bump:

  • Flush the cache wholesale (some other connection wrote and the update_hook didn't fire for us).
  • Fan out a table == "" notification to subscribers, meaning "treat all tables as potentially modified."

Worst-case staleness for external writes: about one second. Tunable per pool if your workload needs tighter.

Subscribe API

Anything that caches state derived from the database can subscribe to write events and invalidate in lockstep: 

sub := fastdb.Subscribe(func(table string) {
    // table == "" means "all may have changed"
    myCache.InvalidateForTable(table)
})
defer sub.Close()

Callbacks run on the writing connection's thread (inside SQLite's hook). Keep them short. The renderer's output cache uses this: one subscription invalidates rendered-page entries the moment a relevant row changes.

Per-table bypass — why and how

A table that takes thousands of writes per second wastes cache work if we keep invalidating + re-populating. fastdb detects the pattern automatically:

  • Each invalidation increments the table's writes-in-window counter.
  • If writes-in-window exceeds bypassWriteThreshold (default 200/sec), the table flips to bypass for bypassCooldown (default 5 sec).
  • Queries touching that table skip the cache during bypass. Other queries on quiet tables stay cached.
  • After cooldown the table re-enters normal operation.

Net effect: write-heavy tables don't poison the cache for the rest. Read-heavy tables stay aggressively cached. No per-installation tuning required.

What fastdb deliberately doesn't do

  • It's not a generic SQLite library. Read-only from this package's perspective; writes still go through the standard modules/db path. The split exists because read patterns and write patterns want very different connection pool shapes.
  • No automatic prepared-statement param caching by value. Today the cache keys on the raw SQL string. WHERE id = 1 and WHERE id = 2 are two separate cache entries. Bind-value support is a planned extension, not present today.
  • No incremental view maintenance. Writes invalidate, they don't update-in-place. For workloads where re-render after a write becomes the bottleneck, this is where IVM would slot in — not built yet.
  • No mid-row escape hatches. A query either cacheable in full or skipped entirely. Per-row staleness tolerance isn't a knob.

Why this exists separately

Stdlib database/sql is generic; it can't expose SQLite-specific things like update_hook or data_version. Generic Go cache libraries (Ristretto, BigCache, freecache) don't know about SQL, so they can't drive table-level invalidation. fastdb sits in the gap: a SQLite-aware cache that the rest of the engine subscribes to. We own it because every cache layer above it (the renderer's, future ones) needs the same write-event channel to stay correct.
