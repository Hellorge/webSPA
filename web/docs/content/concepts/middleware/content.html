Middleware

Per-route hooks that run before the handler. Each one can short- circuit the chain. The engine provides the machinery; you decide what auth, rate limiting, audit, or anything else looks like for your site.

The shape

A middleware is a function: take a RouteCtx, return true to continue or false to short- circuit. A short-circuit means the handler does not run; the middleware is responsible for having written a response. 

type Middleware func(c *RouteCtx) bool

Examples in shape:

func requireAuth(c *RouteCtx) bool {
    user := lookupSession(c.Req)
    if user == nil {
        c.Resp.HeadID = head401
        c.Resp.Body = []byte("Unauthorized")
        return false
    }
    // attach to ctx so the handler can read user
    return true
}

func auditLog(c *RouteCtx) bool {
    log.Printf("%s %s", c.Req.Method, c.Req.Path)
    return true   // always continue
}

Registration

Middleware are global by name. Modules call actions.RegisterMiddleware in their init(): 

func init() {
    actions.RegisterMiddleware("auth", requireAuth)
    actions.RegisterMiddleware("audit", auditLog)
}

Re-registering an existing name panics — conflicts surface at startup, not at request time.

Per-route declaration

Routes opt in by listing middleware names. They run in declaration order, before the handler: 

{Path: "api/posts/:id", Method: "DELETE",
 Middleware: "auth, audit",
 ActionID: DeletePost}

The build packs the names into the manifest's MiddlewareBlobs section as length-prefixed strings, one group per route. At server load, the names are resolved against the registry into a function-pointer slice cached on appState.mwChain[manifest][routeIdx]. Unknown names fail the load — better than silent no-op at request time.

What the engine deliberately doesn't provide

gogogo ships the middleware machinery, not the middleware. There is no built-in auth, no built-in rate limiter, no built-in user model. Those are application concerns — what counts as "logged in", what a role is, how rate-limit policies are scoped, what storage to use for sessions — varies wildly across apps.

Optional reference modules (e.g. modules/auth when it lands) will register middleware under common names ("auth", etc.). Apps that want them import the module. Apps that don't write their own.

Why this shape

  • Names, not IDs. Build emits string names; runtime resolves them. New middleware = new registration. No renumbering, no schema collision.
  • Always-on cross-cutting stays inline. Things every request needs (request ID generation, metrics, the future gogolog) live in the dispatcher's main path. Middleware are for per-route opt-in.
  • Single-phase, no post-hooks. If a middleware needs to act after the handler, it sets up state via RouteCtx the handler reads back. Keeps the chain a simple for-loop with one branch.
  • Hot path stays minimal. No middleware on a route → zero work. One middleware → one function call, one bool check. The pooled RouteCtx is the only allocation, and only when the route needs one.
