Output cache

The fastdb row cache eliminates the SQL cost on hole pages. The output cache eliminates the rendering cost too. It stores the fully-assembled page bytes — envelope spliced with hole output, optionally brotli/gzip pre-encoded — ready for writev. Hits skip SQL, template execution, splice, and compression.

What's cached

One outputEntry per (manifest, holeOffset) pair. Each entry holds three encoded variants: 

type outputEntry struct {
    variants [3]variantBody  // indexed by encoding: identity, gzip, brotli
    tables   []string      // the SQL tables this page reads from (for invalidation)
}

type variantBody struct {
    body []byte
    head uint16   // pre-registered HTTP response head with Content-Encoding baked
}

The shape mirrors RouteEntry.Variants[3] on the static side. Encoding is an array index, lookup is one deref, no search. Same model for cached and built-in static; same code path picks the variant.

Lifecycle of one request

  1. Trie matches the URL → routing entry.
  2. Action is ActionStatic with a non-zero HoleOffset → output cache lookup.
  3. Hit: pick variant by Accept-Encoding, set resp.HeadID, slice the body. Done. Zero render work.
  4. Miss:
    1. Compose the identity body via composeHoleBody — envelope + SQL + per-row template + splice.
    2. Compute compress.Brotli(body) and compress.Gzip(body).
    3. Compute the union of all holes' table sets.
    4. Store the three-variant entry under the holeKey; register the entry in reverse[table]→set[holeKey] for each referenced table.
    5. Pick variant and serve.

Invalidation

The output cache subscribes to fastdb at startup: 

st.outputCacheSub = fastdb.Subscribe(st.outputCache.Invalidate)

When fastdb sees a write — via sqlite3_update_hook on a pool connection or via data_version bump — it fans out to subscribers. The output cache:

  • For a named table: walks reverse[table], drops every entry that references it, and cleans the table's reverse-index slot.
  • For table == "" (external write detected by data_version): flushes everything.

Next request for an invalidated page misses and re-populates from fresh data. Invalidation is O(entries-touching-this-table), not O(cache-size).

What's not cached, and why

  • Pages whose SQL is too complex to attribute. If any hole's SQL is a CTE, subquery in FROM, or uses quoted identifiers we can't extract from, the page is marked uncacheable — we can't know which write should invalidate it.
  • Routes with no holes. Pages that are pure-static don't need the output cache; their compressed variants are baked into the manifest at build time and served from mmap directly.
  • One-shot dynamic URLs. Routes with params/catch-all DO cache (key includes bindings hash), but unique-each-time URLs (per-session UUIDs, ad tracking IDs) churn the LRU and effectively never hit. That's the same "no cache" outcome as bypass would give, without needing a special code path.

Bounded growth

Dynamic routes create one cache entry per distinct (route, bindings) pair. Without bounds, a high-cardinality URL space (e.g. /users/:id with 10M users) would fill memory. The cache caps at 4096 entries or 32 MiB (whichever hits first), with LRU eviction.

  • Hot URLs stay cached (LRU promotes on hit).
  • Cold URLs get evicted (LRU evicts from tail).
  • Static URLs (no bindings) all share the params == 0 slot — one entry per page, same as before.

Why this layer earns its place

Before output caching, hole pages did SQL + per-row template + splice on every request. With output caching, that work runs once per write event instead of once per read. Read-heavy workloads see hole pages serve at near static-page QPS. Write-heavy pages degrade gracefully through fastdb's per-table bypass — if a table thrashes invalidations, the output cache stops caching pages that touch it, and they fall back to the row-cached render path.

Layering

The three caches that compose for hole pages:

LayerWhat it cachesInvalidated by
Output cache Full rendered + compressed HTML per page Write to any table the page reads
fastdb row cache Materialised SQL rows per query Write to the query's tables
Template parse cache Parsed text/template per hole body Manifest reload (SIGHUP)

Each layer is independent — output cache misses fall through to row cache, which falls through to SQLite. All three share one invalidation signal: fastdb's write events.
