gogohttp

The transport library that sits below gogogo. It speaks HTTP/1.1 over TCP, hands the engine a parsed Req, and writes out a Resp with one writev per response. It knows nothing about routes, templates, or SQL. That's gogogo's job. This is the network seam.

Boundary

gogohttp does this:

  • Accept TCP connections (SO_REUSEPORT-fanned bouncers, one per CPU).
  • Parse HTTP/1.1 requests from byte streams.
  • Hold a pre-baked-head registry (Status + Content-Type + Server + …) indexed by uint16.
  • Write responses: pick the head bytes by HeadID, gather them with the body, write via net.Buffers (one writev syscall when the kernel supports it).
  • Manage keep-alive timeouts and connection lifecycle.

It does not:

  • Know about routes, paths, methods, params.
  • Interpret any specific header (Accept-Encoding, Cache-Control, Authorization — all just bytes to gogohttp).
  • Render anything. The body is opaque []byte.
  • Import anything from gogogo. It's a separate package.

The Req/Resp model

type Req struct {
    Method  Method
    Path    []byte
    Host    []byte
    Headers []Header  // every header line, name and value as byte slices
    Body    []byte
}

type Resp struct {
    HeadID uint16      // index into the registry
    Body   []byte      // opaque payload
    Stream func(io.Writer) error  // optional streaming hook for sendfile etc.
}

Byte slices instead of strings throughout the hot path — they alias the read buffer, no copy until the handler asks for one. Headers iteration is a slice walk; the engine decides which names it cares about.

The head registry

Every distinct HTTP response head is registered once and indexed. Examples: 

id := reg.AddMime("text/html; charset=utf-8")
id := reg.AddMimeWithEncoding("text/html; charset=utf-8", "br")
id := reg.AddAllow("GET, POST")

Each AddX assembles the canonical head bytes once (HTTP/1.1 200 OK\r\nContent-Type: …\r\nContent-Encoding: …\r\nServer: Gogogo\r\n) and returns its registry index. At response time the engine sets resp.HeadID = X; the writer concatenates registry[X] + body + "\r\n" via net.Buffers.

Net effect: no per-request fmt.Sprintf for headers, no string assembly, no map allocations. The cost of "set Content- Type and Server and the status line" is reduced to a uint16 store.

Encoding variants on the engine side

gogohttp doesn't know what Accept-Encoding means. gogogo does. The engine stores three head IDs per encoded resource (one each for identity, gzip, brotli), looks at the request's headers, and sets resp.HeadID to the right one. 

func pickVariant(entry *router.RouteEntry, req *gogohttp.Req) *router.Variant {
    // gogogo's logic — gogohttp stays out of it
    for i := 0; i < req.NHeaders; i++ {
        if !bytes.EqualFold(req.Headers[i].Name, []byte("Accept-Encoding")) {
            continue
        }
        v := req.Headers[i].Value
        if entry.Variants[router.EncBrotli].DataLen > 0 && bytes.Contains(v, []byte("br")) {
            return &entry.Variants[router.EncBrotli]
        }
        if entry.Variants[router.EncGzip].DataLen > 0 && bytes.Contains(v, []byte("gzip")) {
            return &entry.Variants[router.EncGzip]
        }
        break
    }
    return &entry.Variants[router.EncIdentity]
}

Why the split

Web frameworks usually bundle the transport with the application protocol — one library handles both raw TCP framing AND knows what Accept-Encoding means. That couples decisions that should stay independent.

With the split: changing how we negotiate encodings doesn't touch the parser. Adding a new compression (zstd) is an engine-side variant slot; gogohttp doesn't learn anything new. Swapping the parser for an io_uring backend doesn't break encoding negotiation. Each library does one thing.

SO_REUSEPORT bouncers

On Linux, gogohttp opens N listening sockets on the same (host, port) using SO_REUSEPORT. The kernel hash-distributes incoming connections across them. Each bouncer is an independent acceptor + connection processor goroutine pool, so there's no single accept lock to contend on. N defaults to runtime.NumCPU(); the only tuning knob.

The response write

A typical response leaves the engine like this: 

resp.HeadID = 22           // pre-baked text/html|br head
resp.Body = cachedBytes  // mmap'd or cached []byte

gogohttp's writer assembles a 3-element net.Buffers: the head, the body, the trailing "\r\n". One writev syscall sends them all. No fmt.Fprintf, no buffered writer flush, no chunk-encoded re-buffering. On Linux when the body is a file descriptor (actions.ActionFile), the writer falls through to sendfile instead — bytes go kernel-to-kernel.
